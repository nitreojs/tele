# encrypted messages

An experimental, off-by-default envelope for ordinary private chats and Saved Messages. Both participants need a compatible client and must compare public-key fingerprints through a trusted channel. It is separate from Telegram Secret Chats. Existing messages are not converted.

## using it

1. Set a local app passcode, then enable **tele → debug → encrypted messages (experimental)**.
2. Open a private chat's **⋮ → encryption → encryption keys**. On a new device, restore an existing encrypted backup before creating a new device key.
3. Copy only the public key. For another person, use **verify encryption key**, paste their public key, and compare the displayed fingerprint in person or through another trusted channel. Check the confirmation only after comparing it. Saved Messages uses your own key and needs no contact verification.
4. Choose **encryption → enable automatic encryption** in that chat's menu. New supported text, file and photo sends from the normal composer are encrypted before the normal Telegram transport. Turning this off requires a separate confirmation that future messages will be readable to Telegram.
5. Authenticated text is decrypted locally as it becomes visible. A native lock beside the message date appears only after successful authentication with the expected key and context. Ordinary readable messages in the same chat do not receive the lock. **Copy decrypted text** deliberately copies the visible plaintext; ordinary copy, quotes, forwards and exports keep the canonical ciphertext.

The normal composer preserves supported formatting and custom emoji, splitting long text into at most 64 encrypted parts. A complete authenticated group appears as one message; missing or unavailable parts retain their part numbers. The separate one-off editor remains limited to 1,024 UTF-8 bytes. Unsupported peers, paid chats and unsupported send types are rejected without sending readable text. Scheduling, edits, polls, voice messages, inline results and forwarding into an automatically encrypted chat are currently blocked. The separate **encrypted message** editor and **decrypt message** dialog remain available for deliberate one-off use.

Automatic mode is account- and chat-specific and binds the selected identity and verified contact key. Missing, changed or unavailable keys block sending. Disabling the experimental master option also blocks already configured chats; explicitly turn off automatic encryption for a chat to return it to ordinary sending. The default empty configuration leaves ordinary Telegram behavior unchanged. Automatic-chat selections are local settings and are excluded from settings import/export.

Protected drafts stay only in memory and are discarded on lock, account switch, mode removal or exit. New local/cloud draft serialization, compose scripts, inline queries, remote previews, translation and calculator requests are blocked for protected compose fields. Activation clears the ordinary cloud draft and removes the native persisted draft files; a failed cloud clear is reported. It cannot undo a draft already seen by Telegram, remove independently saved content or control another client.

The legacy plaintext text cache holds at most 64 messages and 128 KiB; the rich-text group cache has a separate 128 KiB bound. Six CPU decryption jobs are available: three reserved for normal viewing and three shared by viewing and search. Normal viewing uses the reserved slots first and can use all six when search is idle. Search cannot use the reserved slots. Only visible eligible messages are scheduled automatically; multipart messages can inspect up to 128 loaded neighbors to authenticate the complete group. Opening a chat does not scan its full history. Lock, logout, account switch, key changes, option changes and duress invalidate pending results and clear the local plaintext display/cache. The canonical history model remains ciphertext. Qt/OS allocations can retain copies; this is not a forensic-erasure guarantee.

## searching protected chats

Telegram cannot search the readable body of these encrypted envelopes. A configured private chat uses on-device search in the existing chat-search interface. The query is kept in memory and excluded from recent search terms. The local path remains selected when keys are locked, unavailable or the master option is off; it returns no decrypted results instead of sending the query to cloud search.

A search examines up to 2,000 loaded candidates and 8 MiB of source text, with at most 200 results. **Search older encrypted history** downloads at most 400 older messages per click through ordinary history requests containing no search query. This is a bounded search window, not a persistent full-account index. Downloads still reveal the requested chat and timing to Telegram. Complete authenticated multipart groups produce one result at the first part. Results use native ciphertext preview rows; opening a result uses the local decrypted chat view. There is no plaintext search index on disk. Query changes, lock, account/key/mode changes and duress cancel pending work and clear results.

## files and photos

**Encrypted file** encrypts a file before uploading it as a generic `message.teleenc` document. Its original filename and body stay inside the authenticated encrypted payload. No plaintext caption or thumbnail is uploaded. Decrypt from the message's context menu and explicitly choose where to save the plaintext; it is not opened automatically.

With automatic encryption enabled, the normal attachment path prepares up to four files, 16 MiB per file and 32 MiB per batch, in a background job. Files are sent individually as generic encrypted documents. Captions are sent first as separate encrypted text messages through the same formatting and multipart path, before file preparation starts. Batch delivery is not atomic; a network failure can leave a caption or incomplete message without its file. Unsupported edits, animations and special attachment options fail before uploading rather than silently sending their original content. Normal photos use fresh-PNG metadata removal and preserve aspect ratio while resizing to at most 2,000 pixels per side. **Send as document** preserves document presentation. Other file types keep their internal bytes and metadata inside encryption.

New normal photos decrypt locally into native photo bubbles. Clicking opens a guarded local image preview; **Save** deliberately writes a plaintext PNG. The ordinary document/file download policy still applies because the transport is encrypted: disabled automatic file downloads require a download tap before the image appears. Legacy encrypted files and documents retain their ordinary encrypted-file tile and explicit decrypt/save flow. No readable photo or thumbnail is uploaded.

Only visible eligible photos are scheduled, with one download/decryption pipeline and a global cache of at most three images and 64 MiB. Already rendered images and previews clear before cache eviction, lock, account/key/mode changes or duress. Ephemeral photo objects are not registered in the canonical session model or handed to the global media viewer. The normal message, forwarding, drag and export paths continue to carry the encrypted document. These controls do not guarantee erasure of copies retained by Qt, the GPU or the operating system.

The payload, including its filename and framing, is limited to 16 MiB. The encrypted upload can be roughly twice that size because it includes a sender copy and a recipient copy. Downloads may use a temporary file containing ciphertext only.

**Remove metadata from photos** is checked in the send dialog. Supported photos are decoded with orientation applied, then written as a fresh PNG containing pixel data. EXIF, GPS, ICC, text and resolution chunks are omitted, and the inner filename becomes `photo.png`. Unsupported images, images reported as multiframe, excessive decoded sizes and oversized output fail before uploading. Frame recognition depends on the installed Qt image reader. The picture can still reveal location, identity, watermarks or other information in its pixels. Clear the checkbox to send videos, documents or other files with their internal metadata encrypted rather than sanitized. Saving a decrypted file deliberately creates plaintext on disk.

## keys and backups

Each Telegram account has a separate, randomly generated P-521 private key. Telegram IDs and network selection bind authentication context; they do not generate the key. A client build contains no shared decryption secret. Nothing in this feature uploads a private key or a backup passphrase.

The local key store uses Telegram's encrypted per-account storage and requires a local passcode. A damaged or unreadable store does not silently create a replacement identity. Restoring a different identity over an existing identity is rejected.

**Encryption keys → encrypted key backup** exports the private key only in a password-protected `.telekey` file. Its public key is derived again on import. The passphrase must contain at least 16 Unicode characters; five randomly selected words are preferable to a predictable sentence. The password is not stored with the backup. The file uses PBKDF2-HMAC-SHA256 with 600,000 iterations, a random 16-byte salt, and AES-256-GCM with a random 12-byte nonce. The backup is authenticated to the same Telegram account and network.

Keep the backup off the device and its passphrase separately. Restore it on another device signed in to the same account to read the same content. Contact verification records are not exported: verify contacts again before receiving or sending private-chat messages on the other device. Your own sent copies and Saved Messages can be read after restoring your identity without importing a contact pin. Public keys can be copied separately and are not secret. Replacing a contact's pinned public key can make older incoming messages unreadable until the previous public key is restored. Losing the private key and all usable backups loses access to that identity's messages.

An exported backup remains usable by anyone who obtains it and its password. Deleting a local key cannot revoke an external copy. Local passcode protection, buffer clearing and file deletion cannot guarantee forensic erasure from SSDs, swap, hibernation files, crash dumps, backups or a compromised operating system.

Local keys also have an ordinary account lifecycle. Signing out removes that account's local encryption-key files. Removing the app passcode or switching off app locking removes every registered local encryption-key file before the native master key can become unprotected. The existing logout/passcode confirmations and app-lock description include a backup warning. Cleanup happens first and cannot be undone if the later native passcode write fails. A cleanup or registry error keeps app-passcode protection in place. Changing one nonempty app passcode to another retains the keys. Keep the bounded registry with the profile; removing or rolling it back outside the app is outside this protection.

## duress and local code display

The duress extension is being validated with the desktop integration. It is off by default. **tele → debug → duress password** requires the ordinary app passcode, a separate confirmed password and an explicit acknowledgment of key loss. An ordinary app passcode accepted by the native verification path takes priority. Duress cleanup is suppressed if native password-key derivation is unavailable or the native check supplies no key-availability evidence. Changing the ordinary passcode attempts to disarm duress protection; configure it again afterwards.

Entering the duress password at the normal lock screen persists a blocked state before attempting to remove every enrolled account's encrypted-message key-store variants. The lock screen remains locked and follows its ordinary incorrect-passcode path. It does not announce a duress success or offer recovery. Encrypted-message tools become unavailable for blocked account slots; normal key creation cannot replace their removed identity. Unused, provably keyless slots remain available for their first identity. Deliberate recovery starts from **tele → backup → restore encrypted key**, using an off-device encrypted backup and its separate password. Each restored account is unblocked individually.

Accounts stay signed in by default. **Sign out after duress** configures the current account's exact selected sessions. Other selected devices are attempted first. When this device is selected, a 30-second deadline attempts native local logout even if other devices could not be signed out. It still requires the matching authorized session and a successfully persisted local intent; storage or lifecycle failures can prevent it. Remote requests need internet access and Telegram permission; a cold, locked start cannot execute them until the account becomes available. Clearing local credentials offline is not confirmation that the server revoked the session. Failed or unconfirmed remote sign-outs remain reported as such. Pending requests are bound to the original login session and do not automatically target a replacement login or newly added device. A last-account logout can remove the normal app lock and show the login screen, following upstream behavior. Changing configured selections affects future activations and does not cancel already recorded jobs. These optional actions are not a guaranteed remote wipe.

**Decoy login codes after duress** is a separate, off-by-default local display option. Its future-event duration defaults to 24 hours and accepts 1–720 hours. During an activation, code-like digit spans in incoming official Telegram service messages are replaced in the local text model used by copy and preview consumers; translation results use the same replacements. Coverage of native views and copy routes still requires manual validation. The helper recognizes numeric patterns, not the semantic meaning of every login message. Different formats may be missed and other code-like numbers may match. Each replacement differs from that message's matched original; it is not guaranteed different from every unknown valid code elsewhere.

Real updates and codes still enter process memory. Originals are retained only in RAM to restore the local display at expiry. This does not modify Telegram cloud history, other clients, raw protocol data, developer logs, data exports, existing clipboard history, OS notification archives or screenshots already made. A person controlling the account or operating system can bypass display concealment. The absolute expiry is persisted; restart does not start another 24 hours. A changed system clock or rolled-back profile can defeat this local policy. Changes to duration or the future-event option do not shorten an activation already in progress. A damaged display-policy file suppresses service text until an explicit passcode-confirmed repair from duration settings.

The state files and ciphertext messages can reveal that the feature exists. File deletion cannot guarantee an absence of Windows traces or forensic recovery. Exported backups remain valid. An altered client or a restored pre-duress profile can bypass local blocking. See the [duress design and validation requirements](sealed-duress-design.md) for the exact boundaries.

## protocol and limits

The native build requires OpenSSL 3 or later. The envelope uses authenticated HPKE from [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html): mode 2, DHKEM(P-521, HKDF-SHA512), HKDF-SHA512 and AES-256-GCM. The selected P-521 suite targets roughly 256-bit classical key-agreement strength, following the size mapping in [NIST SP 800-57](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-57pt1r5.pdf). AES-256 has a 256-bit key; its GCM authentication tag remains 128 bits. Password strength, entropy failures and compromised devices are separate limits. Each public-key fingerprint uses SHA-512. Every record uses a fresh encapsulated key and a single-shot sequence number of zero. Sender authentication requires an already verified sender public key supplied by the caller; a key supplied inside an untrusted message is never trusted.

Attachment presentation is part of the authenticated inner `TELEFILE` payload. Legacy version 1 always represents a document. Version 2 adds a one-byte document/image hint before the filename and content lengths; unknown values fail closed. Image presentation requires the generic inner name `photo.png` and a bounded, successfully decoded RGBA8 PNG containing only CRC-checked `IHDR`, `IDAT` and `IEND` chunks. Transport filenames, MIME types and thumbnails cannot supply this hint. New Image payloads are smoothly resized to at most 2,000 pixels per side after applying orientation; the existing 16-megapixel input bound remains. Document sanitization keeps full dimensions and fails if the result is oversized, without resizing implicitly. The outer file HPKE format is unchanged.

The authenticated application context is one byte for Telegram test/production network, followed by the sender and recipient IDs as unsigned 64-bit big-endian integers. The role, context length, context and complete envelope header are bound into domain-separated HPKE info and AEAD associated data. Each envelope carries a recipient record and a sender record. Saved Messages uses the same format with the same identity on both sides.

Text is zero padded to a fixed 1,028-byte plaintext before encryption. Its complete `tele-sealed:v1:` token is 3,155 ASCII characters. Files use 64 KiB padding buckets. These reduce exact-length disclosure; they do not hide traffic, accounts, destinations, timestamps, IP addresses, file-size buckets, deletion, forwarding or the fact that encrypted envelopes are in use. Telegram can still withhold, delete or replay ciphertext. The stateless format has no replay tracking or forward secrecy: compromise of a retained identity key exposes its retained history, including sender copies. It is not a ratcheting conversation protocol and has not received an independent security audit.

The new rich-text codec keeps short unformatted text compatible with version 1. Its `tele-sealed:v2:` parts preserve bounded native formatting and custom-emoji tag IDs in a canonical encrypted payload, split into at most 64 parts. Only a fresh random group ID, part index and part count are public. The complete payload hash and exact length are encrypted inside every part, and the public header is authenticated with the account/chat context. A complete group must authenticate, have unique indices and pass the whole-payload hash before formatting is decoded. Missing, mixed or duplicate parts produce no partial plaintext. Native send/merge/render integration still requires application validation.

The machine-readable [wire-format description](../tests/sealed/protocol-v1.json) and [standalone regression tests](../tests/sealed/README.md) are intended for interoperability work. The current implementation is desktop code. An iOS client, its integration and device testing are separate work; an Apple signing certificate alone cannot turn this desktop project into an IPA.

## validation

The standalone suite compiles the actual product crypto and photo/file helpers. A separate pure passcode-gate target checks normal-verdict precedence, absent or failed native-key evidence, failure persistence and nested scope restoration; it does not run a native KDF or lock screen. It checks official HPKE vectors, both envelope records, self notes, wrong keys/context, malformed encodings, tampering, padding boundaries, backups and photo metadata. An independent Python implementation decrypts emitted C++ envelopes and backups. Storage tests use a narrow facade and do not substitute for running Telegram's real storage implementation.

Before proposing this feature for release, exercise the native app with disposable data:

- With the option off, verify ordinary menus, send behavior and drafts.
- With it on, verify passcode requirements, explicit first-key creation and restore-before-create on a second device.
- Exchange and compare two accounts' keys. Reject a changed key, an unchecked verification, a wrong account, a wrong password and a damaged backup without replacing any working key.
- Send and decrypt UTF-8 text in both directions and in Saved Messages. Check the 1,024-byte boundary and ensure plaintext never appears in a normal draft, request log, notification preview or cloud history.
- Enable automatic mode, use the ordinary composer and attachment picker, and inspect actual transport from another client. Confirm authenticated text and its separate lock, readable-message distinction, failed-key blocking, visible-only processing, bounded cache, deliberate plaintext copy and all invalidation paths. These new native flows are still being validated.
- Send a photo with GPS/EXIF, then clear metadata removal for a generic binary file and an empty file; decrypt and compare content. Inspect the actual uploaded document name, absence of thumbnail/caption, and cleaned photo metadata.
- Cancel dialogs and downloads. Lock, switch account, log out and disable the option while an editor, decrypted view or background operation is open. Confirm no late callback reveals or sends content.
- Confirm blocked and paid chats preserve editor text and upload nothing.
- Test ordinary logout, passcode removal and app-lock disable. Wrong proof must preserve keys; nonempty rotation must retain them. Test blocked deletion, all three variants, and a native-save failure after deletion while protection remains.
- With a stale duress password equal to the current ordinary passcode, inject native Argon2/scrypt failure and verify no activation change or key deletion, then test successful ordinary verification. These native fault-injection and warm/cold lock-screen checks remain pending.
- Exercise the [duress, recovery, decoy and selected-signout checks](sealed-duress-design.md#required-checks-before-shipping), including warm/cold locks, unused accounts, stale callbacks, expiry/repair and local-only versus server-confirmed logout. Use mocked session requests before any deliberate test-account operation.

A passing standalone suite is not a claim that the native dialogs, operating-system integrations or mobile clients have been tested.
