# Encrypted-message duress design

Status: implemented, with native validation pending. The bounded filesystem helpers and facade targets have standalone tests; complete native behavior has not been validated. This document describes local key removal and an optional temporary local login-code display filter. It does not describe secure erasure, a hidden Telegram account, or revocation of exported keys.

## Agreed behavior

A separately configured duress passcode is entered into Tele's ordinary app lock screen. It removes this profile's encrypted-message private keys and verified peer keys from Tele's active stores. Telegram accounts remain signed in by default. The default lock screen stays locked and follows its ordinary wrong-passcode path. Separately selected logout rules are described below; logging out the last account can instead lead to Telegram’s normal login screen. It must not announce that duress was recognized, show a success toast, offer recovery, or pretend that a cold-start account was unlocked.

Encrypted-message tools disappear for blocked account slots; unused, provably keyless slots remain available for their first identity. Recovery requires deliberately opening a documented recovery action and supplying an encrypted key backup kept off this device and its separate backup passphrase. There is no automatic recovery dialog and no undocumented gesture. The deliberate entry point is **tele → backup → restore encrypted key**. It remains available for explicit recovery; no recovery prompt appears automatically after duress.

The duress option and the optional login-code decoy mode default to off. Enrollment is explicit, explains irreversible loss without an off-device backup, and confirms a distinct duress passcode. Reauthentication with the ordinary local passcode is required before enrollment or changing duress protection. The ordinary app passcode is never saved by the duress module.

## Existing unlock path

Both the main lock screen and the unlock box use `Window::TryPasscode` in `window/window_lock_widgets.cpp`. It checks empty input and the existing flood limit, makes a cleansed UTF-8 copy, and calls `Main::Domain::tryPasscode`. The latter serializes attempts and runs the expensive derivation on a worker. Cold attempts start the storage domain; warm attempts only verify the passcode.

Before a cold unlock, no account sessions or decrypted account key stores exist. A verifier inside the encrypted-message account store therefore cannot recognize duress at startup. Making the duress passcode successfully open Telegram at startup would require another wrapper for Telegram's master local key and a storage-format design. This proposal intentionally keeps the app locked instead.

## Smallest viable integration

The `tele_sealed_duress.cpp,h` integration coordinates the separate state, setup UI, code-display and selected-signout modules. A small include-and-call hook in `Main::Domain::tryPasscode` runs immediately after `_passcodeDeriving = true`. Both lock surfaces reach that method through `Window::TryPasscode`. Existing empty/flood checks remain outside it. An inspection of callers found no separate native caller to bypass this path.

The worker boundary is `DerivePasscodeWithDuress(nativeJob, typedBytes, normalDone)`, where `normalDone` receives the derived job and a `finalize(correct)` function. When no duress configuration exists, it delegates exactly to `Storage::DeriveOnWorker`. With enrollment present, the same serialized attempt verifies duress and derives the native passcode job on a worker. The main-thread callback checks the ordinary native verdict first, then runs a finalizer: an ordinary passcode accepted by the native path always wins. An incorrect verdict can trigger cleanup only with a matching duress verifier and observed successful native-key availability. Missing evidence or any observed derivation failure suppresses cleanup. This prevents native KDF unavailability from being treated as a confirmed password rejection when a normal-passcode change collides with a stale duress configuration. Keep `_passcodeDeriving` held across the complete decision. Both completion paths release it once, apply cold/warm, quitting and domain-lifetime guards on the main thread, run `result = finalize(correct)` while the attempt is still held, release the attempt flag, then invoke `done(result)`. Correct ordinary verification may also attempt to disarm a colliding duress configuration, but its failure must never cause a wipe. The helper must not start two independent jobs, release the attempt flag between checks, or hold an uncleaned typed-byte copy in a GUI callback.

The pure `tele_sealed_passcode_gate.h` policy uses a scoped thread-local observer around the synchronous `normalDone` call. Both cold `derived.keyFor(...)` paths and warm `checkPasscode` report whether a native key is available. A true observation means the native key calculation was available, not that the password was correct; the ordinary native verdict still decides that. The gate requires at least one successful observation and refuses cleanup after any failed observation. Paths that reject missing or unsupported state before observing a key also suppress cleanup. Nested scopes restore the previous observer, and the shared gate remains alive through the finalizer. With no observer, the hook preserves its input and native behavior.

The `sealed_passcode_gate` regression target compiles this actual pure header. It checks the verdict/match matrix, absent and failed evidence, both orders of mixed success/failure observations, inactive-hook behavior and nested scope restoration. It does not inject failure into real Argon2/scrypt, run the worker-to-main callback chain, or validate either native lock surface. Those integration checks remain pending.

The duress trigger path, which requires an incorrect ordinary verdict, never opens Telegram’s native master key. No wallet verification or other password dialog becomes a duress trigger. Do not add another passcode wrapper or change Telegram’s account-key format merely to simplify this hook. There is no claim that timing, filesystem effects or later behavior make duress indistinguishable from a wrong password.

Tele-only APIs provide storage availability checks, guarded enrollment, blocked-state notifications and a deliberate recovery transaction. Storage methods check blocked state themselves; menu visibility alone is insufficient. The ordinary native passcode verification remains the deciding unlock verdict.

## Startup-readable configuration

Store a small versioned configuration scoped to the current working directory and `cDataFile()` profile, outside account encryption because it must be usable before cold unlock. Request owner read/write permissions where honored, use atomic replacement and strict fixed limits, and use a supported fixed KDF cost with a random salt and domain-bound verifier. Qt file permissions do not establish a private NTFS ACL on Windows; inherited directory permissions still apply. Compare verifier bytes in constant time. Never store either passcode as text. KDF parameters are not arbitrary attacker-controlled work factors.

Enrollment records a bounded manifest of only this profile's exact encrypted-message store locations. Current stores are under the account `user_<data name>/` directories and are named `tele_sealed_keyss`, `tele_sealed_keys0`, or `tele_sealed_keys1`. Derive the manifest from real account storage locations during enrollment; include newly added accounts before allowing new encrypted-message keys to be written. Limit the manifest to 1536 account directories and 4608 fixed variants, matching the current supported account maximum, plus a fixed path length and a fixed total encoded size.

On every use, resolve paths against the intended `tdata` root, reject absolute paths, traversal, links, and paths outside that root, and accept only the exact expected account directory and three fixed leaf names. Do not recursively scan or erase arbitrary files. These canonical-path checks are not handle-relative atomic no-follow operations; they reject stable unsafe paths, not a hostile process concurrently replacing directories or links. Missing manifest entries, invalid configuration, or an unrecognized blocked-state format must fail closed for encrypted-message operations, without deleting unrelated files. Telegram authorization, wallet, normal message, draft and settings files are outside the cleanup set.

This configuration and the blocked marker are themselves local traces. A configuration readable before login cannot be promised invisible to a person inspecting the filesystem.

## Trigger and cleanup transaction

1. Verify the duress passcode within the serialized attempt, after the existing empty/flood checks.
2. Atomically persist a new blocked generation, fresh activation ID, activation UTC timestamp and cleanup-pending marker before removing any key file. Activation ID/time remain stable through cleanup, registration, enrollment, disarming and per-account recovery; only a new trigger replaces them. Check write completion; do not claim protection was armed if that marker could not be stored. Atomic replacement alone is not a promise about every power-loss or storage-cache failure.
3. Advance the in-process generation, close and clear encrypted-message dialogs, and cancel their pending results. Workers must check cancellation before expensive work where possible and again before publishing any result. Private-key wrappers, decrypted byte arrays and passphrase owners cleanse their memory when released. An OpenSSL operation already running cannot safely be forcibly interrupted; its result must be discarded and its owners released.
4. Block previously used or unsafe/unknown account slots, retaining every previous blocked bit; leave provably keyless unused slots available. Remove all three exact store variants for every blocked slot, including old/fallback copies. Treat each filesystem failure as pending cleanup, never as successful erasure. The app remains blocked and retries safe cleanup on startup. Avoid logging passcodes, plaintext, private keys, or a duress-success event.
5. Complete through the ordinary incorrect-passcode path. Keep the app locked by default. Key-store cleanup itself sends no Telegram request; separately selected signout actions may run once an authorized session is available.

Use a profile-wide activation ID with per-slot blocked/recovered records and a separate mutation generation for compare-and-swap updates. Every load, create, verified-peer update and ordinary restore must refuse a blocked account at the storage boundary. Restoring account A must not unblock account B or let B silently generate a replacement key. Unused account slots and newly registered keyless slots remain available for their first encrypted-message identity. Trigger blocks a slot only when an exact key-store variant exists, a previous blocked record already exists, or filesystem status is unsafe/unknown. Re-enrollment never clears a known blocked record just because its files have been deleted. Send, decrypt and backup operations use live dialog/session guards, cancellation state, storage gates and relevant current-key comparisons before publishing results. Blocking notifications close and clear affected dialogs. There is no blanket captured-generation comparison in every callback; the explicit mutation-generation check belongs to the state and recovery transactions. Native cancellation and reentrancy testing is still required to establish that pre-duress work cannot publish afterward.

The existing key backup export is not deleted automatically. Backups previously saved on this device, clipboard contents, files explicitly saved after decryption, and copies outside the manifest are not covered by key-store cleanup.

## Deliberate recovery

An explicit documented recovery action accepts an off-device `.telekey` backup and its separate passphrase. It validates the backup's authentication, account/network binding and private/public key consistency before offering a deliberate restore. It must not accept a normal unlock passcode, a fresh random key, or an undocumented click sequence as recovery material.

A dedicated recovery transaction rechecks account identity and the captured mutation generation, writes the authenticated restored key store synchronously, and only then records that account as recovered. The successful state write advances its mutation generation while preserving the activation ID. It does not clear the deny state for other accounts. If any step fails, ordinary storage operations remain blocked. A crash between writing the key and recording recovery leaves that account blocked rather than silently enabling keys. Recovery must not clear a newer duress generation produced while its worker or file picker was open.

The current manifest binds quarantine to an account-slot directory, while the private key store itself checks its Telegram owner/network stamp. Reusing a known blocked slot for a different owner stays conservatively blocked; the wrong owner cannot restore the old owner’s backup. That situation needs the original valid backup in its original account or a new isolated profile. Moving identities between slots is not a supported owner-wide quarantine mechanism. A future blocked-owner map needs a separate versioned binding design; silently replacing the old slot owner would lose its deny record.

This is an application policy, not cryptographic revocation. A modified client can ignore the blocked marker. Someone can roll back a complete pre-duress data copy, remove or alter the marker, or decrypt an exported backup in another program if they have its password. No local import gate can invalidate an exported private key.

## Ordinary logout and app-lock removal

Every private-key-store write first atomically registers its validated account directory in a separate bounded profile registry. Entries remain registered after cleanup and failed writes. The registry contains directory names, not private keys or account authorization. It does not scan user folders. Ordinary logout removes only the three sealed-key-store variants before destroying the native session. A failed deletion retains the registry across restart so a later logout or passcode-removal attempt can retry. Ordinary registry cleanup is not automatically scheduled merely by restarting.

Removing the app passcode or disabling verified app locking performs the same cleanup after the ordinary proof check and before persisting an unprotected master-key wrap. A cleanup guard excludes private writers until the native operation has finished. An unknown, corrupt, busy or incompletely cleaned registry refuses that weakening of storage protection. Ordinary nonempty passcode changes retain the encryption keys. A profile that never created a registry or a key file keeps ordinary upstream behavior, including unsupported, linked, nonexistent and non-directory unused storage roots. Known unsafe registered paths fail closed.

The existing logout and passcode confirmation text warns about key loss and the need for an off-device encrypted backup with its separate password. Deletion happens before the native passcode update, so an update that fails afterward can still have removed the encryption keys; that ordering is stated in the existing confirmation. No extra permission prompt is introduced. Copies already exported, filesystem recovery, rollback and hostile concurrent path changes remain outside the deletion guarantee. Requests for owner permissions do not establish Windows NTFS access-control isolation.

The actual registry and store facade are exercised with temporary files, writer/deletion failures, strict parsing, permanent registration, unrelated-file sentinels and Windows junctions. Native logout, proof verification and failed passcode-update flows still require the full desktop build and manual lifecycle testing.

## Optional temporary login-code decoys

Latest requested behavior replaces displayed Telegram login-code digits with decoy digits for a user-configured period after duress. It keeps the service chat and Telegram account signed in. This separate option defaults to off; the configured duration defaults to 24 hours. Do not silently hide other security notices.

On duress, persist a bounded UTC expiry and a fresh random activation seed before returning to the lock screen. Load this state before sessions can display notifications, history or search results after restart. A monotonic timer handles expiry while running; persisted UTC handles restart. Changing the system clock or rolling back the profile can defeat this ordinary local expiry policy; it is not a trustworthy security clock. Before expiry, no normal rendering or copy action should reveal the original matched digits. At expiry, invalidate the affected layouts and previews and restore ordinary display. Do not replay old notification banners.

Do not delete service messages, drop Telegram updates, mark messages read, change server notification settings, confirm a login, approve an authorization, log out, or revoke sessions. Keep raw Telegram protocol messages and network data unchanged. The chosen native integration deliberately replaces the local HistoryItem text model during the period and retains its real original only in a per-session RAM cache for restoration. The server receives no replacement code. A decoy must differ from the original matched code and will not authenticate as that original code; a failed attempt or comparison with another client can reveal that the display was altered. This is not protection against someone who controls the account or the device.

`SpoilerLoginCode` in `history/history_item.cpp` provides a matching reference. It finds the first digit/hyphen span of 5–8 characters for the Telegram notifications peer, checks some entity overlap, and inserts a spoiler entity. It is used by `notificationText` and `toPreview`; it neither semantically identifies a login nor changes the original text. Its broader 4–8 character handling of the separate Verify Codes peer is outside the requested Telegram-login scope. Ordinary digits, dates and other messages can match the heuristic, and differently formatted or future login messages can be missed. Treat this as an explicit detection limitation, not complete recognition in every language.

The Tele helper identifies only peer777000 using PeerData::kServiceNotificationsId; isNotificationsUser() would also include333000. It transforms code-like spans in a copy of TextWithEntities at HistoryItem::setTextValue. Preserve UTF-16 length, punctuation and entity offsets. Derive a stable decoy from the activation seed, account/message identity and original code, so history, preview, copy and restart show the same replacement throughout the activation. Ensure the replacement differs from the matched original. Never change authentication callbacks or raw protocol data. Track loaded message IDs before activation, cache originals only while active, and restore the latest cached original at expiry. Avoid masking an already transformed value again, including a translation requested from the displayed decoy. A newly translated numeric span that equals an existing replacement is indistinguishable from that replacement; recognition remains heuristic. Clear records when items or their sessions are removed.

The helper needs consistent integration at all display/copy boundaries:

- Notification text and native/custom notification actions. Invalidate queued previews and clear already displayed notifications for the service history when decoy mode starts, so a cached original code does not remain visible. `Window::Notifications::System::clearFromHistory` exists, but OS notification archives may retain previously displayed content.
- Chat-list previews, cached preview rows, in-app chat previews, pinned/reply snippets, and search-result snippets. Search-result and translation callbacks begun before duress must transform their results against current state before display.
- Main history text layouts, translated text, open and secondary windows, selection, accessibility text, context-menu copy and code-copy buttons. Rebuild already loaded layouts on activation and expiry. A copy handler must read the current transformed value at action time rather than retain original digits captured before activation.
- Local/global and cached message search, jump-to-message views and other surfaces that construct text independently from `notificationText` or `toPreview`.

The central setter covers consumers of the local text model, including originalText() copy paths, with a second hook for late translation results. Native view and clipboard coverage still requires testing. Scripting's `777000` filter prevents service updates reaching ordinary script handlers but still delivers them to the native app; it must not be repurposed to discard updates. `Scripting::HiddenInList` affects only `History::shouldBeInChatList` and is irrelevant to replacing code digits. Generic preview hiding or notification spoilers alone leave the real code available elsewhere. History selection and quote paths also read originalText() directly, which is why this version changes that local model instead of using only a layout overlay. Code-bearing clickable URL entities are removed, including percent-encoded targets, to avoid hidden original codes or clickable decoys invoking authentication.

Raw account data remains real by design. Telegram cloud history, other clients, data exports, account scripts with permission, logs or dumps already produced, previously copied text, OS archives and filesystem inspection can expose it. Automatic translation, forwarding, quoting, exports and developer/script surfaces require an explicit review: do not claim comprehensive concealment while any such path can display or emit the original code. Preventing those paths would expand this display-only feature substantially. The protocol and raw model must continue to process genuine Telegram updates correctly.

The implemented native module has a separate reproducible facade target using the actual product source with synthetic application/history/timer/UI objects. That target exercises persistence, mappings, expiry and failure paths; it does not validate the real HistoryItem hooks or native views. A malformed existing policy record, or an active/requested policy write failure, suppresses local service text until deliberate repair. The duration dialog offers an explicit reset warning that originals may become visible, followed by ordinary-passcode verification and an atomic reset to future decoys off. No repair prompt appears automatically. The full desktop build and native coverage tests remain required before claiming complete behavior.

## Optional selected session logout

The default is to keep every account signed in. Enrollment may separately select, per account, logout of this device and termination of specifically selected other authorized sessions. This is an additional opt-in action, not a prerequisite for key removal or decoy mode. It changes Telegram account/session state and must be named clearly when configured. Never perform real termination while merely testing the UI or parsing the configuration.

Persist selections with the Telegram account ID, test/production network, local account identity and selected authorization hash, plus enough stable enrollment metadata to reject an ambiguous or mismatched refreshed session. Do not identify sessions by a translated device label, row position, active timestamp or IP address. `Session::uniqueId()` is the user ID with a test-network bit, not a unique authorization-session ID. A later login by the same Telegram user must not silently inherit an old this-device logout rule without matching the enrolled authorization identity.

Refresh authorization data before executing a pending remote rule. For each exact selected account/hash, accept only one matching current authorization with the expected identity attributes. An absent entry is not evidence that another similarly named device should be terminated. Reject duplicates, zero/current entries in the remote list, stale mismatches and ambiguous metadata. Never replace a stale selection with all sessions or a guessed device. Raw authorization data retains the server hash, current flag and creation date; the existing `Api::Authorizations::Entry` normalizes this device to hash zero and does not retain creation date, so that presentation list alone is insufficient for the strongest identity check.

`Api::Authorizations::requestTerminate` accepts an optional hash. A missing hash sends the all-other-sessions RPC. The duress implementation must always pass the validated nonzero selected hash, or use the single-session `account.resetAuthorization` RPC directly. It must never invoke the broad reset path as a fallback. Leave unselected devices untouched. An explicit successful server response, followed where feasible by refreshed authorization state, is needed to record confirmed remote termination; a request queued, timed out or canceled is not success.

For a loaded account, the queue attempts selected remote sessions first. If this device was also selected, a separate 30-second deadline requests local credential clearing after the activation when the matching authorized session is available, including when remote requests are offline or rejected. Cold startup still waits until that matching account becomes available. The fallback attempts the native forcedLogOut path, cancels this module’s owned request sender, persists its local intent first, and checks the exact local binding and authoritative pending job again. A missing session, stale state or failed intent write can prevent the action; the deadline is not a guarantee despite storage or lifecycle failure. It is local credential removal, not proof of server revocation. If remote targets remain unconfirmed when local credentials disappear, persist a terminal partial result and do not retry them using a later replacement login. Remote-only jobs can retain pending retries with bounded backoff. Do not claim unconfirmed sessions were revoked. Changes to configured selections affect future activations; they do not cancel the job snapshot already recorded for an active event.

At cold startup, recognizing duress does not decrypt or start accounts. Record pending session actions and perform no remote action until an ordinary unlock has made the correct account session available. Do not secretly retain a copy of Telegram authorization keys or store the real passcode to bypass this constraint. Pending rules should be stored with minimum metadata and bound to the activation generation; a later unrelated login must not accidentally execute them. Their storage is another local trace.

For an explicitly selected this-device rule, own the `auth.logOut` request and then use native `Main::Account::forcedLogOut` while the matching session still exists; do not manually delete Telegram authorization files. Ordinary `Main::Account::logOut` also completes its callback on RPC failure and does not reset the retained MTP authorization keys, so its callback alone is insufficient for this local credential-removal policy. Record server confirmation separately from local removal. An error or timeout can still clear this device locally without proving server revocation. Cancel the module's owned sender and recheck the authoritative activation, selected job and exact local binding before forcing cleanup.

Logging out the final account normally calls `Main::Domain::removePasscodeIfEmpty`, which clears the native app passcode and opens the ordinary login screen. This is a material exception to staying locked and follows native logout behavior; the default signed-in path stays locked. The independent encrypted-message quarantine must survive native logout/passcode clearing, so neither re-login nor normal settings reset automatically restores removed encryption keys. Native logout also has its ordinary account/cache effects; the narrowly scoped key-removal operation itself still does not erase unrelated Telegram or wallet files.

## Required checks before shipping

Test disabled behavior against upstream, used account A versus unused B and new C, retaining A’s deny after file deletion/re-enrollment, unsafe paths, conservative blocked-slot reuse, enrollment failures, distinct normal/duress passwords, warm and cold lock screens, both unlock surfaces, flood/busy states, wrong passwords, shutdown during derivation, multiple accounts, account addition, malformed/oversized configuration, links and traversal, and all store suffixes. Inject blocked-marker and deletion failures and crash points before/after each transaction step. With optional signouts off, verify key cleanup changes no Telegram authorization, wallet or ordinary account files. Optional logout deliberately invokes native account cleanup and has its normal account/cache effects.

Inject native Argon2/scrypt unavailability and derivation failure while a stale duress password equals the current ordinary passcode after a failed disarm write. Verify no new activation, no key deletion and no optional actions on both warm and cold lock screens. Restore successful native derivation and verify the ordinary passcode wins. Also exercise missing/unsupported native wrap state and changed-wrap derivations. These native KDF-injection and lock-screen checks remain pending; the pure gate matrix is not their substitute.

Test ordinary logout and app-lock removal separately: wrong proof leaves keys untouched, a nonempty passcode rotation retains keys, successful removal deletes all three variants before unprotection, and obstructed cleanup retains native protection. Inject a native passcode-save failure after cleanup and verify keys are already gone while protection remains. Check unused profiles create no registry or lock files.

Start send, decrypt, file-save, export and restore operations before locking, then trigger duress and verify that their callbacks cannot recreate keys or reveal plaintext. Test recovery with wrong password/account/network, old or different backups, and a newer duress generation while recovery is pending. Confirm the normal key-creation path cannot bypass the block.

For optional decoy mode, test real Telegram-code fixtures in supported languages, false positives and missed formats, stable same-message replacements, original-code inequality, notifications already visible and arriving later, previews, selection, copy actions, accessibility, translated/quoted text, open and secondary windows, direct links, local/global and cached searches, restart before expiry, expiry while running/locked, and clock changes. Confirm raw Telegram protocol messages remain unchanged, no login is approved, the user remains signed in, and normal display returns at expiry. Inspect export, script and log paths separately and state their limits. For optional logout, use mocked RPCs for selected-account/hash matching, duplicate/stale/current hashes, absent sessions, explicit single-session requests, remote-before-local ordering, partial failure, offline and cold pending actions, later unrelated login, timeout, stale callbacks after a newer activation, durable-intent write failures, local-only offline fallback, server acknowledgment versus local-only completion, future-rule edits retaining active jobs, cancellation and last-account cleanup. Verify unselected accounts/devices receive no action and no broad revoke-all request is ever constructed. Never terminate real sessions during automated tests. No implementation is complete until the dev build and these native flows are exercised.
